# F-044 — Generic Scheduled-Job Infrastructure (Phase 1)## ContextThis platform has never had real scheduled infrastructure. `POST /bookings/sweep` ([index.ts:2509](services/slot-engine/src/index.ts:2509)) carries the comment *"In production this runs as a cron/background job"* — **that cron job does not exist anywhere in this repo**; its only callers are two regression tests. F-043 Phase A dodged the problem entirely with lazy on-access generation. Nothing has ever run on a timer.F-044 identifies three use cases sharing one need — something firing proactively with no user action: (1) admin notified before a guest-slot pattern expires, (2) guest reminded a booked slot is approaching, (3) member reminded their confirmation cutoff is approaching.**This phase:** build the generic mechanism, prove it end-to-end with **use case 3 only**. Use cases 1 and 2 become new job files plus a registration line — that is the point of building generically, not a promise to ship all three now.**Why use case 3 first** (confirmed): its trigger condition is already computed by proven code — F-022's cutoff math exists identically at [index.ts:554](services/slot-engine/src/index.ts:554) and [index.ts:677](services/slot-engine/src/index.ts:677). No new business rule is needed to know *when* to fire, so the phase tests the scheduler rather than a new rule.---## The core architectural decision**Chosen: in-process timer, in a dependency-free generic package, mounted in slot-engine.** (Option 1, refined.)*Not option 3 (Cloud Scheduler):* contradicts the established genericity/portability goal, and requires a publicly-reachable trigger endpoint — the exact shape that produced F-053. Production routing is still undecided (F-004).*Not option 2 (6th service):* a new always-on container on one VM already running Postgres + 5 Node services + Caddy, each capped at `--max-old-space-size=96` ([Dockerfile.node-service](deploy/gcp-vm/Dockerfile.node-service)). The design keeps promotion cheap — the runtime is a package, so mounting it elsewhere is one `createScheduler()` call.*Why slot-engine, not Notification:* all three use cases' trigger conditions read slot-engine's data. Notification owns *delivery*, not domain state, and the codebase enforces that boundary — [notification/index.ts:51](services/notification/src/index.ts:51) does a cross-service HTTP lookup rather than reading `User` directly, because *"Notification service does not own the User table."* A scheduler in Notification would either break that boundary or call back into slot-engine to ask "what's due?" — option 3's shape with extra steps.### The interface boundary (what makes genericity provable)**`packages/job-scheduler` has zero runtime dependencies — including no Prisma.** This matters concretely: the Prisma client ships as `@badminton/database`, so importing it would put a vertical's name directly into the "generic" package's dependency list, and would open a *third* `PrismaClient` pool in slot-engine (it already has two: [index.ts:18](services/slot-engine/src/index.ts:18) and [availabilityGeneration.ts:9](services/slot-engine/src/availabilityGeneration.ts:9)) against `max_connections=30`.The package defines a **port**; the host implements it against its own client:```ts// packages/job-scheduler/src/types.tsexport interface ScheduledJobStore {                       // implemented by the host service  claimDueJob(name: string, leaseSeconds: number): Promise<boolean>; Idempotency — the real dedup mechanism**Stated plainly: the dedup guarantee is a real database-level unique constraint — `@@unique([jobName, dedupKey])` on `ScheduledJobDispatch` — not an application-level check.** Two processes racing to remind the same member both attempt the INSERT; Postgres admits exactly one and the loser gets P2002. Application code never decides who wins, so there is no read-then-write window to lose.This deliberately mirrors the two patterns already proven in this codebase: `GenerationLock`'s `@@unique([resourcePoolId, date])` with P2002 tolerated ([availabilityGeneration.ts:171-182](services/slot-engine/src/availabilityGeneration.ts:171)), and F-022's partial unique index enforcing one active assignment per member — where the schema comment states the rationale exactly: *"making concurrent assignment requests fail with P2002 rather than relying on app-level pre-checks"* ([schema.prisma:249-252](packages/database/prisma/schema.prisma:249)).There are **two independent guards, and the constraint is the one that actually matters.** The SQL job claim prevents two instances running the same job tick; the unique constraint prevents a double-send even if the claim were bypassed, buggy, or removed. They are proven separately in verification, because a test that only exercises the claim would pass on a design whose ledger did nothing.```claimDispatch()  → INSERT status=PENDING; P2002 → already handled, skip (no send)POST /notifications/send  (with an idempotency key)markDispatched() → status=SENT   └─ on POST error: failDispatch() → status=FAILED, attempts++```**Dedup key: `{userId}:{windowId}` — deliberately no calendar date.** `windowId` already identifies the occurrence uniquely (a window belongs to exactly one date), which is why [`memberBookingIdempotencyKey`](services/slot-engine/src/index.ts:624) keys on it. Omitting the date component removes any dependency on the UTC/local-date ambiguity described in Finding B below — a scheduler crosses midnight *every day*, so this is not hypothetical.**Retry is by status predicate, never by row absence.** A crash between INSERT and POST leaves `status=PENDING` with nothing sent; retrying on *row absence* would treat that as "already done" and lose the reminder permanently. Retrying `status IN (PENDING, FAILED) AND attempts < 3` recovers it. Rows are never deleted on failure — the audit trail ("were they ever reminded?") is a real support question, and deleting destroys it.**Making that retry safe requires one small change to Notification:** `NotificationRequest.idempotencyKey String? @unique`, accepted by `/notifications/send` and returning the existing row on P2002. Without it, retrying a POST whose response was lost in transit double-sends, because [notification/index.ts:99-112](services/notification/src/index.ts:99) creates a fresh row on every call. This reuses the pattern already proven in this repo — `Booking.idempotencyKey @unique` ([schema.prisma:284](packages/database/prisma/schema.prisma:284)) with P2002 recovery at [index.ts:745-751](services/slot-engine/src/index.ts:745). **Flagged as a scoped addition** (~15 lines + one field): it is what makes requirement #1 actually hold rather than approximately hold. Strike it and the design falls back to strict at-most-once, losing reminders in the crash window.### 2. Missed-check recovery — stated behavior**Bounded catch-up via live re-query, with deliberate drop of stale reminders. No replay log.**Handlers re-query current domain state each tick; the due predicate is a **range**, not an instant:```cutoff - reminderLeadMinutes  <=  now  <  cutoff - guardMinutes```- Down for part of the range → next tick after restart fires it, late but useful. `nextRunAt` is already past at boot, so the job is immediately due; the first tick runs ~5s after boot rather than waiting a full interval.- Down for the **entire** range → **deliberately dropped, not queued.** "Your cutoff is approaching" sent after the cutoff passed is worse than silence.- Down for hours → `nextRunAt` is stale by hours, producing **one** run, not a backlog burst. This coalescing is documented as a package contract, since it is the design's most surprising property.Correctness never depends on any individual tick firing. A startup assertion enforces the invariant this relies on: `rangeWidth >= 3 × interval`.### 3. Check frequency — derived from the smallest supported trigger window, not chosen**The 30-minute grace period is a default, not a floor — this was checked, not assumed.** `PUT /resource-pools/:id/booking-rule` validates `gracePeriodMinutes` only as `Number.isInteger(value) && value >= 0` ([index.ts:1451](services/slot-engine/src/index.ts:1451)), so `1` is a legal configuration. `POST /booking-rules` applies **no validation whatsoever** ([index.ts:1413](services/slot-engine/src/index.ts:1413)). The real floor is **0**. Sizing the interval against 30 minutes would have been sizing against a number an admin can change from the Admin Web UI.So the interval is stated as a **constraint**, not a preference. For a reminder to be reliably deliverable:```usableRange = min(leadMinutes, cutoffOffsetMinutes) - guardMinutesguardMinutes    >= 2 x tick + deliveryLatency        (sweep-collision guard, see the job design)jobInterval     <= usableRange / 3                    (>=3 chances; survives 2 missed ticks)```With `tick = 60s` and `guard = 3 min`, `jobInterval = 60s` requires `usableRange >= 3 min`, i.e. **`gracePeriodMinutes >= ~6`** for the mechanism to give meaningful notice.**Revised from the earlier draft:** the reminder job runs **every 60s, same as the tick** — not 300s. A 5-minute interval only looked adequate because it was measured against a 30-minute window; against a legally-configurable 6-minute window it could miss the range entirely. The cost of 1440 runs/day versus 288 is one indexed query either way.**Below the viable threshold the job skips the pool and logs `SKIPPED_WINDOW_TOO_NARROW`** rather than firing a reminder that arrives after it is actionable. It degrades visibly instead of silently doing something useless.This generalizes to the other two use cases: each `JobDefinition` declares `minimumViableWindowSeconds`, and `createScheduler()` **asserts at startup** that `3 × tickMs <= minimumViableWindowSeconds` for every registered job. A future job with a tighter window fails loudly at boot rather than quietly under-firing in production.**Performance flagged, not optimized away (rule 2):** the due-query scans `MemberGroupAssignment WHERE status='ACTIVE'` across all tenants, now 1440×/day. Trivial at current scale; at thousands of assignments it is a repeated table scan, and the real fix is narrowing by branch/time-bucket, which this phase deliberately does not build.### 4. Delivery — reuse, explicitly**Reuses the existing Notification path entirely** — the handler POSTs to `/notifications/send` exactly as the sweep does ([index.ts:2637](services/slot-engine/src/index.ts:2637)), inheriting channel-policy routing, retry/backoff and dead-letter. No parallel delivery infrastructure.**No new event type.** `slot_release_reminder` already exists in the policy matrix ([notification/index.ts:20](services/notification/src/index.ts:20)) as `['sms','push']` — *"both — time-critical, cannot rely on push alone"* — precisely this reminder's semantics. Specced since Phase 5 and queued only by tests; this gives it its first real producer. `CHANNEL_POLICY` is unchanged.> **Known limitation of the layer underneath (F-054, not fixed here).** `processQueue()` has exactly one production caller — [notification/index.ts:117](services/notification/src/index.ts:117), a `setImmediate` fired only when a *new* notification is submitted. A reminder whose first dispatch attempt fails will not retry on its 1/5/15-minute ladder unless an unrelated notification happens to be sent later. The reminder's *queueing* is reliable; its *retry* is not. Not assumed away.---## Technical Design### Schema — `packages/database/prisma/schema.prisma````prismamodel ScheduledJob {  name                String    @id  enabled             Boolean   @default(true)  intervalSeconds     Int                      // CHECK (> 0) added as raw SQL in the migration  timeoutSeconds      Int       @default(60)  nextRunAt           DateTime  lastRunAt           DateTime?  lastRunStatus       String?                  // SUCCESS | FAILED | TIMEOUT  lastRunError        String?  lastRunDurationMs   Int?  consecutiveFailures Int       @default(0)  lockedUntil         DateTime?                // lease — a crashed run is retried, not silently skipped  createdAt           DateTime  @default(now())  updatedAt           DateTime  @updatedAt  @@index([enabled, nextRunAt])}model ScheduledJobDispatch {  id           String    @id @default(uuid())  jobName      String  tenantId     String?                         // nullable — platform-level jobs have none  subjectId    String?                         // queryable ("was this member reminded?") without LIKE  dedupKey     String  status       String    @default("PENDING")   // PENDING | SENT | FAILED | ABANDONED  attempts     Int       @default(0)  lastError    String?  occurrenceAt DateTime?  expiresAt    DateTime?  dispatchedAt DateTime?  createdAt    DateTime  @default(now())  updatedAt    DateTime  @updatedAt  @@unique([jobName, dedupKey])                // THE dedup guarantee  @@index([jobName, status, createdAt])        // retry scan  @@index([expiresAt])                         // prune scan}```Plus `NotificationRequest.idempotencyKey String? @unique` (see question 1), and `BookingRule.confirmationReminderLeadMinutes Int @default(30)` — following the existing convention that time policies are admin-configurable there alongside `gracePeriodMinutes` / `guestAccessCutoffMinutes` / `lowOccupancyThresholdPct`.`String` not enums for status fields, matching `NotificationRequest.status` and `AvailabilityPattern.status`. No FK from `jobName` — matches the existing *"Scalar UUID, no DB relation yet"* convention and avoids blocking job renames. Migration: `20260808_______scheduled_jobs_f044`.**Retention:** `ScheduledJobDispatch` is never read after its tick, and use case 2 would add one row per booking forever. `expiresAt` + a `pruneDispatches` batch helper (`take: 1000`, so it cannot lock the table) ship with the runtime now; registering it as a job is a one-line follow-on.### The claim (multi-instance guard) — raw SQL, not `updateMany````sqlUPDATE "ScheduledJob"   SET "nextRunAt"   = now() + make_interval(secs => "intervalSeconds"),       "lastRunAt"   = now(),       "lockedUntil" = now() + make_interval(secs => "timeoutSeconds") WHERE "name" = $1 AND "enabled"   AND "nextRunAt" <= now()   AND ("lockedUntil" IS NULL OR "lockedUntil" < now())RETURNING "name";```Exactly one caller gets a row. Under READ COMMITTED a second transaction blocks on the row lock, then re-evaluates the predicate against the committed new version, matches zero rows, and returns nothing.**Why raw SQL rather than `prisma.scheduledJob.updateMany`:** the re-check only works if the predicate is a flat `WHERE` on the updated column. If Prisma emits the `WHERE id IN (SELECT …)` form, the outer predicate is unaffected by the first update and **both callers claim the job**. Staking mutual exclusion on an ORM's SQL-generation strategy across future upgrades is not acceptable for a correctness primitive. Raw SQL also lets the claim use the **database clock** — with two instances on skewed clocks, a JS-computed `now` makes "due" a per-process notion. `updateMany` cannot express `now()` or a column-relative interval at all. Identifiers are quoted throughout, per F-051's raw-SQL/Prisma-casing lesson.`nextRunAt = now() + interval` (not `previous + interval`): drift is harmless against a range predicate, whereas fixed-slot scheduling produces a backlog burst after downtime.### Failure isolation- Per-job try/catch (`Promise.allSettled`) — one handler throwing must not abort the rest of the tick.- **The tick callback must never reject.** `setInterval(async () => …)` with an unhandled rejection is **fatal in Node 20**, which would take slot-engine's entire HTTP API down. Always `setInterval(() => { tick().catch(log) }, ms)`.- Re-entrancy guard so a slow tick does not stack.- Two timeout layers: `AbortSignal.timeout(5000)` per outbound fetch (the existing call at [index.ts:2637](services/slot-engine/src/index.ts:2637) has none, and undici has no overall request timeout), and a per-handler race against `timeoutSeconds` recording `lastRunStatus='TIMEOUT'`. `lockedUntil` is the backstop, since racing does not cancel JS work.- `consecutiveFailures` with backoff, so a permanently broken handler cannot hammer the DB every 60s forever.- Graceful shutdown via Fastify `onClose` → `clearInterval` + await the in-flight tick.### The first real job — `services/slot-engine/src/jobs/memberConfirmationReminder.ts`**Eligibility is not restated — it is extracted and shared.** The confirm endpoint enforces four conditions ([index.ts:2308-2340](services/slot-engine/src/index.ts:2308)): active subscription, `now < cutoffTime`, booking not `RELEASED_NO_SHOW`, and not already confirmed. A reminder that ignores any of these tells a member to confirm something the server will reject with 409. This is exactly the failure F-022 already caught once — *"the sweep's existing auto-release logic would have silently un-confirmed a member's own valid confirmation"* — two places computing one rule, drifting.So: extract `canMemberConfirm(resolution, subscription, now)` and have **both** the confirm endpoint and the job call it. Handler logic:1. Load `MemberGroupAssignment WHERE status='ACTIVE'` matching today's ISO weekday, reusing the ±1h window-matching from [index.ts:505-516](services/slot-engine/src/index.ts:505).2. `cutoffTime = window.startTime - rule.gracePeriodMinutes` — F-022 math, unchanged.3. Range filter `[cutoff - confirmationReminderLeadMinutes, cutoff - guardMinutes)`. If the pool's usable range falls below the viable threshold (question 3), skip it with `SKIPPED_WINDOW_TOO_NARROW` rather than sending a reminder that cannot arrive in time to be acted on.4. `canMemberConfirm(...)` must be true — re-checked **immediately before dispatch**, not only at query time.5. Claim → POST → mark.**The guard band matters.** Sweep step 2 releases at exactly `window.startTime - gracePeriodMinutes` ([index.ts:2536-2543](services/slot-engine/src/index.ts:2536)) — the same instant the reminder range would otherwise end. Without a guard band, a reminder computed at cutoff−5s lands after the seat is already released: "Confirm now!" → 409. `guardMinutes >= 2 × tick + delivery latency`.The handler stays strictly read-only — it never calls `ensureTodayMemberBooking`.**Notification payload (F-029/F-037 discipline):** `variables` carry `poolName`, slot `startTime`, `cutoffTime` — human-meaningful fields only. No `userId`, `windowId`, or `bookingId`, which would render into an SMS as raw internal identifiers. (The existing `low_occupancy_alert` call does pass a raw `poolId` at [index.ts:2650](services/slot-engine/src/index.ts:2650); this payload deliberately does not copy that.)### Mounting — `services/slot-engine/src/index.ts````tsconst scheduler = createScheduler({ store: prismaScheduledJobStore(prisma), jobs: [memberConfirmationReminderJob], tickMs });if (process.env.SCHEDULER_ENABLED === 'true') scheduler.start();```**Default OFF.** The regression harness spawns real service processes ([test-harness/src/process.ts:62](packages/test-harness/src/process.ts:62)), so an auto-starting timer would mutate shared DB state underneath every other suite's assertions. Tests call `runDueJobsOnce()` directly; only production sets `SCHEDULER_ENABLED=true`.**No HTTP trigger endpoint is added** — the existing sweep endpoint is exactly that pattern and is currently unauthenticated and internet-reachable (F-053). Not repeating it.### Edge cases — against the standing categories (rule 7)| Category | Assessment ||---|---|| **Trust boundaries** | No new user-facing endpoint, so no client input to spoof. The member's displayed confirm deadline and its enforced deadline disagree — and a scheduler makes it live.** The member dashboard and confirm endpoint both use `cutoffTime = start − gracePeriodMinutes` (default **30 min**). But sweep step 3 creates an unconfirmed member's booking as `RELEASED_NO_SHOW` at `start − guestAccessCutoffMinutes` (default **120 min**, [index.ts:2592-2609](services/slot-engine/src/index.ts:2592)), and confirm rejects `RELEASED_NO_SHOW` outright ([index.ts:2326-2331](services/slot-engine/src/index.ts:2326)). So once the sweep runs, the real deadline is T−120 while the UI promises T−30. **Currently dormant only because no cron exists.** Direct consequence for sequencing: **the sweep must not be wired to this scheduler until this is resolved** — doing so would lock members out at T−120, before the reminder range even opens, so the reminder would never fire for exactly the people it targets. This phase is safe because it schedules only the reminder.**B. `todayDateString` is UTC, `isoWeekday` is local time** ([index.ts:616-622](services/slot-engine/src/index.ts:616), repeated in the sweep at [2563/2570](services/slot-engine/src/index.ts:2563)), while `MemberGroupAssignment.startTime` is documented as *"branch local time"* ([schema.prisma:262](packages/database/prisma/schema.prisma:262)) but parsed as UTC at [index.ts:658](services/slot-engine/src/index.ts:658). On an IST container these disagree between 00:00 and 05:30. Dormant because the sweep has only ever been triggered by hand; a 60s scheduler crosses midnight daily. The design above sidesteps it (dedup keys on `windowId`, never a calendar date) but does not fix it.**C. `BookingRule` has no unique constraint or index on `resourcePoolId`, yet 12 sites read `bookingRules[0]` with no `orderBy`** ([index.ts:552](services/slot-engine/src/index.ts:552), [675](services/slot-engine/src/index.ts:675), [2535](services/slot-engine/src/index.ts:2535), [2594](services/slot-engine/src/index.ts:2594), others). Postgres returns arbitrary order, so with two rules on one pool the effective `gracePeriodMinutes` — and therefore the cutoff and the reminder range — can differ between ticks. Mitigated here by adding `orderBy: { createdAt: 'asc' }` at the job's own read site; the constraint itself is a separate decision.**D. `gracePeriodMinutes` has no minimum bound, and the two endpoints that set it validate inconsistently.** `PUT /resource-pools/:id/booking-rule` accepts any non-negative integer including `0` ([index.ts:1451](services/slot-engine/src/index.ts:1451)); `POST /booking-rules` applies **no validation at all** and, because it uses `gracePeriodMinutes ? Number(...) : 30` ([index.ts:1413](services/slot-engine/src/index.ts:1413)), silently coerces an explicit `0` into `30` while accepting a negative value unchanged — a negative would place the confirmation cutoff *after* the window starts. Surfaced by sizing the poll interval honestly rather than assuming the 30-minute default was a floor. This phase degrades safely around it (the too-narrow skip above) rather than fixing it, since adding a floor changes existing admin-configurable behavior.Plus the two already logged: **F-053** (unauthenticated `/bookings/sweep`) and **F-054** (dead retry ladder).---## Files**New:** `packages/job-scheduler/` (`package.json`, `tsconfig.json`, `src/{index,types,runtime,dispatch}.ts`) · `services/slot-engine/src/jobs/memberConfirmationReminder.ts` · `services/slot-engine/src/scheduledJobStore.ts` (the Prisma adapter) · `services/slot-engine/src/regression/scheduled-jobs.regression.ts` · migration · `Implementation_Plan/F-044/` evidence**Modified:** `schema.prisma` (2 models, 2 fields) · `services/slot-engine/src/index.ts` (mount + extract `canMemberConfirm`) · `services/notification/src/index.ts` (accept idempotency key) · `services/slot-engine/package.json` · `regression/run.ts` (explicit section registration, per its [own comment](services/slot-engine/src/regression/run.ts:6)) · `regression/_fixtures.ts` (`cleanDatabase()`) · `deploy/gcp-vm/docker-compose.yml` (`SCHEDULER_ENABLED=true`) · `docs/regression_suite_migration_map.md`---## VerificationRule 8 evidence — real payloads, real logs, real before/after.
