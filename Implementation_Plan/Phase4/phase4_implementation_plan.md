# Implementation Plan — Phase 4: Payment

This plan covers the implementation of the Payment service (`services/payment`). It details database schema updates, slot engine basePrice pricing security changes, webhook idempotency, signature validation, member subscriptions, and the multi-service integration test suite.

## User Review Required

> [!IMPORTANT]
> **Subscription Failure Handling & Auto-Recovery (Fix #1)**:
> - **Notification Trigger**: When a recurring AutoPay debit fails (`subscription.charge_failed` event), the Payment service will transition the `Subscription` status to `suspended` and immediately dispatch a secure API call to the Notification service's `POST /notifications/trigger` endpoint (using `INTERNAL_SERVICE_KEY` auth) with event type `subscription_charge_failed` to alert the user via SMS and Push.
> - **Self-Healing Recovery**: If a transient debit failure resolves (e.g., subsequent daily automated retry by Razorpay succeeds, or the user updates their payment details), receiving a successful `subscription.charged` webhook for that mandate ID will automatically restore the `Subscription` status back to `active`, closing the lockout loop.

> [!IMPORTANT]
> **POST /subscriptions Bookkeeping Design (Fix #2)**:
> - The endpoint `POST /subscriptions` is **purely for database registration and bookkeeping**.
> - The mandate creation is initiated and authorized client-side using Razorpay's AutoPay UI/SDK. Once the mandate ID is generated by Razorpay, the client posts it to this endpoint to record the mapping (linking `userId`, `tenantId`, and `mandateId`).
> - This endpoint does **not** make any outbound requests to Razorpay's API.

> [!IMPORTANT]
> **Atomic Webhook Idempotency Pattern**:
> To prevent concurrency race conditions from dual-captured webhook replays:
> - We will use the **atomic insert-first-catch-constraint-violation** pattern.
> - The webhook endpoint will attempt to insert a `WebhookEvent` with the unique `gatewayEventId` at the very start.
> - If this insert fails with a Prisma unique constraint error (`P2002`), the handler catches the exception and immediately returns `200 OK`, bypassing double-processing.

> [!IMPORTANT]
> **Flat basePrice Decision**:
> For the Basic-tier MVP, we are selecting a **flat basePrice** mapped per `ResourcePool`. While peak/off-peak pricing is a common requirement, a flat base rate is selected here to keep schema layout and scheduling math simple, while still closing the client-supplied pricing spoofing vulnerability.

> [!IMPORTANT]
> **PaymentIntent Duplicate Prevention**:
> To prevent double-charging from double-taps on the UI:
> - `POST /payments/intents` will check if an intent already exists for the given `bookingId` (`referenceId`).
> - If the existing intent is `captured`, we return `400 Bad Request` (`PAYMENT_ALREADY_CAPTURED`).
> - If the existing intent is `pending`, we return the **existing pending intent** (with its UPI link) instead of creating a duplicate checkout session.

We will update the Prisma schema to add the Payment models and extend `ResourcePool` with a pricing field.

#### [MODIFY] [schema.prisma](file:///d:/apps/Platform/packages/database/prisma/schema.prisma)
Extend `ResourcePool` and add Payment models:
```prisma
model ResourcePool {
  // ... existing fields ...
  basePrice           Decimal              @default(100.00) @db.Decimal(10, 2)
  // ... existing fields ...
}

model PaymentIntent {
  id          String   @id @default(uuid())
  tenantId    String
  userId      String
  amount      Int      // in paise/cents (integer)
  purpose     String   // guest_booking | tournament_entry | subscription_billing
  referenceId String   // bookingId or subscriptionId
  status      String   // pending | captured | failed | expired
  gatewayRef  String   @unique
  refunds     Refund[]
  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt
}

model Subscription {
  id        String   @id @default(uuid())
  userId    String
  tenantId  String
  mandateId String   @unique
  amount    Int      // in paise/cents
  frequency String   // monthly
  status    String   // active | suspended | cancelled
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt
}

model Refund {
  id              String        @id @default(uuid())
  paymentIntentId String
  paymentIntent   PaymentIntent @relation(fields: [paymentIntentId], references: [id], onDelete: Cascade)
  amount          Int           // in paise/cents (integer)
  reason          String
  status          String        // pending | processed | failed
  createdAt       DateTime      @default(now())
  updatedAt       DateTime      @updatedAt
}

model WebhookEvent {
  id             String   @id @default(uuid())
  gatewayEventId String   @unique
  createdAt      DateTime @default(now())
}
```

### Payment Service (`services/payment`)

#### [MODIFY] [services/payment/src/index.ts](file:///d:/apps/Platform/services/payment/src/index.ts)
Implement Payment service endpoints:

- **`POST /payments/intents`**:
  - Request body: `{ bookingId: String }`.
  - Check if a `PaymentIntent` already exists for this `bookingId`:
    - If `captured`, throw `400` (`PAYMENT_ALREADY_CAPTURED`).
    - If `pending`, return the existing pending intent.
  - Calls Slot Engine `GET /bookings/:bookingId` (with internal auth key) to verify status is `HELD` and retrieve its `price` and `tenantId`.
  - Creates a `PaymentIntent` in `pending` state with amount in paise.
  - Generates a mock UPI Intent link containing the transaction reference.
- **`POST /subscriptions`**:
  - Purely registers database mapping linking `userId`, `tenantId`, and `mandateId` (bookkeeping for client-side Razorpay setup).
- **`POST /webhooks/razorpay`**:
  - **Signature Validation**: Recomputes SHA256 HMAC of raw payload using `RAZORPAY_WEBHOOK_SECRET` and matches `x-razorpay-signature`.
  - **Idempotency Gate (Atomic Insert-First)**: Inserts `WebhookEvent` with raw gateway event ID. If it fails with `P2002`, catches and immediately returns `200 OK` to reject duplicates safely.
  - On `payment.captured` event: Updates matching `PaymentIntent` to `captured`, and triggers Slot Engine's `POST /bookings/:id/confirm` API.
- **`POST /webhooks/razorpay/autopay`**:
  - Verifies signature and enforces atomic idempotency.
  - On `subscription.charged` event: Creates a `captured` `PaymentIntent` for `subscription_billing`, and updates the matching `Subscription` status to `active` (self-healing recovery).
  - On `subscription.charge_failed` event: Updates matching `Subscription` status to `suspended` and dispatches notification event to Notification service.
- **`POST /refunds`**:
  - Request body: `{ bookingId: String }`.
  - Calls Slot Engine `GET /bookings/:bookingId` to read `refundAmount` and check if status is `CANCELLED`.
  - Verifies that a `captured` payment intent exists.
  - Generates mock Razorpay refund call, creates `Refund` in `processed` state, and returns transaction details.

## Verification Plan

### Automated Integration Tests
We will write a dedicated multi-service integration test suite at `services/payment/src/payment.test.ts` (runnable via `pnpm run test:payment` from the root).
The script will spawn the Payment, Slot Engine, and Identity & Auth servers concurrently, performing the following checks:

1. **Server-Side Pricing & Spoofing Defense**:
   - Seed a ResourcePool with `basePrice = 125.00`.
   - Request a booking hold (`POST /bookings`) passing a spoofed price `body.price = 5.00`.
   - Assert the booking is created successfully but with `price = 125.00`.

2. **Webhook Signature Validation & Security**:
   - Send webhook event with invalid signature. Assert it is rejected with `400 Bad Request`.
   - Send webhook event with valid signature. Assert it is accepted with `200 OK`.

3. **Webhook Idempotency (Atomic Concurrency Test)**:
   - Send the same `payment.captured` webhook payload twice.
   - Assert the first call processes correctly.
   - Assert the second call returns `200 OK` instantly and does not trigger duplicate DB updates or multiple confirm calls.
   - Test payload shape matches Razorpay's actual nested `payload.payment.entity` structures.

4. **End-to-End Webhook Confirmation**:
   - Create a booking hold on Slot Engine (status: `HELD`).
   - Create a payment intent in Payment service.
   - Dispatch a signed mock captured payment webhook payload to Payment service webhook endpoint.
   - Assert the PaymentIntent status flips to `captured`.
   - Assert the Booking status in Slot Engine successfully transitions to `CONFIRMED` via internal confirm dispatch.

5. **Member AutoPay Billing Flow**:
   - Create a member `Subscription` in database.
   - Dispatch a signed `subscription.charged` auto-debit webhook. Verify intent is created as `captured` with purpose `subscription_billing`.
   - Dispatch a signed `subscription.charge_failed` webhook. Verify mandate status flips to `suspended` and triggers notification dispatch mock call.
   - Dispatch a subsequent `subscription.charged` webhook. Verify status heals back to `active`.

6. **PaymentIntent Duplicate Prevention**:
   - Call `POST /payments/intents` twice for the same booking ID.
   - Assert both calls return the same `PaymentIntent` ID (no duplicate intents created).

7. **Direct Refund Execution**:
   - Cancel the booking via Slot Engine cancellation API (status: `CANCELLED`, refund computed based on booking rules).
   - Trigger a refund via Payment service `POST /refunds` passing the booking ID.
   - Assert the payment service reads the Slot-Engine-computed amount and successfully records the refund.
