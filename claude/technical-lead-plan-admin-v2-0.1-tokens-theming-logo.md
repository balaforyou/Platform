Significant deviation: the handover's point 4 (logo on the login screen) doesn't fit admin-v2's own architectureHandover §1.4 says to extend `Tenant.logo` "to admin-v2's login screen and nav shell header." Realcode shows this is only half-buildable: admin-v2 deliberately resolves tenant from the **signed-inadmin's JWT** (`AdminAuthContext.tsx`'s own comment: "admin-v2 deliberately does not use [ui-shared'sTenantProvider]... its tenant comes from the signed-in admin's JWT, not the hostname" — a Slice 1architectural decision). Before login, there is no JWT, so **no tenant is known client-side at all**on `LoginScreen.tsx` — admin-v2 is single-domain (`admin.elitecourts.duckdns.org`) for every tenant,unlike guest-pwa's per-subdomain hostname resolution.**Recommendation (approved by Bala, implement this):** `LoginScreen.tsx` stays generic/fixed-brand(today's `/icon-192.png` + "Slotflow Admin" + system-emerald tokens) — real per-tenant theming andthe real logo apply only **after** auth resolves (`LandingPage`, and later the 0.3 nav shell). Thismatches what Slice 1 already built and requires zero new pre-auth infrastructure.### 2. Judgment call: `--av2-ring` under dynamic themingCould not find the charter's referenced "`--av2-ring` question" spelled out verbatim in the handovertext itself. Real question underneath it: today `--av2-ring` is a fixed `#34d399` in both themes.Once `--av2-accent*` goes tenant-derived, should the focus ring derive from the ramp too?**Recommendation (approved by Bala, implement this): keep it fixed.** Same reasoning as guest-pwa'sown precedent (`--color-accent-2` sage stays fixed/universal under F-190's tenant ramp). `--av2-ring`stays `#34d399` unchanged, decoupled from tenant color.---## Token spec (exact names)### Layer 1 — raw ramp, JS-computed, set on `:root` at runtimeNew: `--av2-accent-100` through `--av2-accent-900` (9 steps), same naming shape as guest-pwa'sproven `--color-accent-100..900` (`apps/guest-member-pwa/src/index.css`), `av2-` prefix to matchevery other admin-v2 token. Computed by `generateAccentRamp()` — already exported from`@badminton/ui-shared` (`packages/ui-shared/src/index.ts`), already a dependency of admin-v2 (usedtoday for `apiRequest`) — **no new package dependency.**### Layer 2 — semantic role tokens (existing names), now aliasing ramp steps with fallbacks`apps/admin-v2/src/styles.css`'s `:root`, `:root[data-theme="dark"]`, and the`@media (prefers-color-scheme: dark)` blocks stop hardcoding hex and instead reference Layer 1 stepsvia `var(--av2-accent-N, <current fixed value>)` — the fallback keeps rendering identical to todayuntil `AdminTenantContext` resolves (or if it ever fails), satisfying evidence item 5 below withoutextra code.| Token | Light | Dark ||---|---|---|| `--av2-accent` | `var(--av2-accent-600, #059669)` | `var(--av2-accent-400, #10b981)` || `--av2-accent-hover` | `var(--av2-accent-700, #047857)` | `var(--av2-accent-300, #34d399)` || `--av2-accent-fg` | `#ffffff` (fixed) | `#04121a` (fixed) || `--av2-accent-soft` | `var(--av2-accent-100, #ecfdf5)` | `var(--av2-accent-900, #06281f)` || `--av2-ring` | `#34d399` (fixed, unchanged) | `#34d399` (fixed, unchanged) |Step choice for `--av2-accent`/`-hover` follows guest-pwa's own convention of using the 600–700 bandfor solid, readable UI fills (`--slot-selected-*` uses `--color-accent-700`). `-fg` stays fixedrather than ramp-derived — no ramp step is guaranteed to need white/near-black text at an arbitrarytenant hue, and fixed values sidestep a contrast calculation not scoped to this slice.**Flagged honestly: dark-mode `-soft` at ramp-900 is a best estimate, not verified pixels** — JBC'sreal `#166534` run through the ramp at step 900 needs a real-browser look before sign-off; if itreads too flat/dark, the fallback is step 800, decided during the real-device review (rule 2:evidence over reasoning), not from code alone.### Spacing scale (new)`--av2-space-1: 4px` `-2: 8px` `-3: 12px` `-4: 16px` `-5: 20px` `-6: 24px` `-8: 32px` `-10: 40px``-12: 48px`. This is an 8px/4px-half-step scale; it doesn't perfectly match every ad hoc valuealready in the five components (Button's `10px 18px` padding, TextField's `9px 12px`) — those getsnapped to the nearest token as part of this slice (see "component retrofit" below), verifiedvisually rather than assumed correct by the math.### Typography scale (new)`--av2-text-xs: 12px` `-sm: 13px` `-base: 14px` `-lg: 16px` `-xl: 20px` `-2xl: 24px`, each pairedwith a `--av2-leading-*` (tight/normal/relaxed: 1.2/1.45/1.6). Font family stays the current`system-ui` stack — nothing in either doc asks admin-v2 to adopt guest-pwa's Inter, and this isn'timporting a brand decision from a different app's finding.### Motion tokens (new — charter §2b, defined here as directed)`--av2-duration-fast: 120ms` `-base: 200ms` `-slow: 320ms`, `--av2-ease-standard:cubic-bezier(0.4, 0, 0.2, 1)`. Plus a global reduced-motion guard in `styles.css`:```css@media (prefers-reduced-motion: reduce) {  *, *::before, *::after { animation-duration: 0.01ms !important; transition-duration: 0.01ms !important; }}```**Animations actually proposed for 0.1** (small surface — most of 0.1 is non-visual plumbing):- **Logo fade-in on `LandingPage`** (`opacity 0→1`, `--av2-duration-fast`, `--av2-ease-standard`) once  the tenant logo `<img>` loads — *rationale: avoids a layout flash swapping the generic icon for  JBC's real logo post-fetch; confirms the real branding arrived, not decorative.*- **No animated crossfade on the accent-color swap itself.** The tenant fetch is a fast local call  and there's no single choke point to animate an app-wide custom-property change safely without  risking jank across every consumer. Explicitly not proposing motion here rather than forcing one in.- Kitchen-sink page: no motion — it's a dev-only review surface, not a real admin-facing flow.---## Architecture — where tenant resolution actually lives`LandingPage.tsx` today does its own one-off `apiRequest('/tenant/tenants/${user.tenantId}')` fetch.0.3's nav shell will need the same tenant record, and the token layer needs it applied **before**any post-auth screen paints, not per-screen. New shared context, following the existing`auth/AdminAuthContext.tsx` naming convention:**New file: `apps/admin-v2/src/auth/AdminTenantContext.tsx`**- `AdminTenantProvider` — wraps children, reads `user` from `useAdminAuth()`, fetches  `apiRequest<AdminTenantBrief>('/tenant/tenants/' + user.tenantId)` once `user.tenantId` exists  (endpoint is no-auth per its own code comment, so no token-timing race). Exposes  `{ tenant, loading, error }` via `useAdminTenant()`.- `AdminTenantBrief` type: `{ id, name, appName, logo, themeColor }` — the endpoint actually returns  the full Prisma `Tenant` row with no field selection (real, pre-existing, out of this slice's  scope to change); the frontend type only declares what admin-v2 consumes, replacing  `LandingPage.tsx`'s local, now-duplicate `TenantBrief` interface.- On resolve, applies Layer 1 tokens to `document.documentElement` via a **pure, separately-testable  function** (see evidence section) — not inline in the effect, so it's unit-testable under the  existing `environment: 'node'` vitest config (no DOM needed for the pure part).**New file: `apps/admin-v2/src/auth/applyAccentRamp.ts`**- `computeAccentRampVars(themeColor: string): Record<string, string>` — pure, wraps  `generateAccentRamp`, returns the 9 `--av2-accent-N` entries. Unit-testable, zero DOM.- `applyAccentRampVars(vars: Record<string,string>, target = document.documentElement): void` — thin  DOM-writing wrapper, calls `target.style.setProperty` per entry. Not unit-tested (matches the  existing vitest comment: "presentational... covered by the Playwright e2e ceremony, not here").**`main.tsx`**: wrap `<AdminAuthProvider><AdminTenantProvider><App /></AdminTenantProvider></AdminAuthProvider>`.**`LandingPage.tsx`**: drop its local fetch/state, consume `useAdminTenant()` instead. Logo `<img>`gets the fade-in transition above.**`App.tsx`**: add the dev-only kitchen-sink gate **after** the existing `isAuthenticated` check(requires real sign-in — reuses the real JWT→tenant path rather than inventing a pre-auth previewpath, consistent with item 1's recommendation above) and before the passkey-prompt gate, so asigned-in review doesn't need to click through the enrol-prompt each time:```tsxif (loading) return <LoadingState label="Checking your session…" />;if (!isAuthenticated || !user) return <LoginScreen />;if (import.meta.env.DEV && window.location.pathname === '/__dev/tokens') return <TokenKitchenSink />;if (!promptResolved) return <EnrollPasskeyPrompt onResolved={() => setPromptResolved(true)} />;```No `react-router-dom` use here — 0.3 owns introducing real routing; this is a plain pathname check,same spirit as the existing `import.meta.env.DEV` gate already used for dev sign-in.**New file: `apps/admin-v2/src/dev/TokenKitchenSink.tsx`** — renders: full color palette (boththemes, via a `data-theme` toggle control on the page itself), typography scale, spacing scale,radii, shadows, and the real JBC logo via `useAdminTenant()`. Dev-only, excluded from the real navper the handover, reached only at `/__dev/tokens` post-login.---## Logo assetNew file: `apps/admin-v2/public/logo-jbc.png` — reuse the exact PNG already committed for guest-pwa(`apps/guest-member-pwa/public/logo-jbc.png`, confirmed real 512×512 PNG, not the original JPEG),copied into admin-v2's own `public/` per its own convention (`icon-192.png`/`icon-512.png` alreadylive there) rather than referencing across apps. `LandingPage.tsx` already renders `tenant.logo` asan `<img src>` — this only requires the asset existing at the path the DB will point to; no DB writehappens in this slice (JBC's `Tenant.logo` is already `/logo-jbc.png` in production, confirmed viacommit `491ae29` and the F-149 register entry's live measurement).## Manifest edge case — answering the handover's open question**Confirmed non-issue.** admin-v2's `public/manifest.json` is static, fixed "Slotflow Admin"branding, and its icons (`icon-192.png`/`icon-512.png`) are already real, correctly-sized PNGs — itnever references `Tenant.logo` or `Tenant.themeColor` at all (unlike guest-pwa's manifest, which isinjected per-tenant at runtime by `TenantContext.tsx` and hit the JPEG/512×512 mismatch). This ismechanical and low-risk, and doing it now avoids the kitchen-sink page being the only thing on thenew tokens while shipped components silently diverge. Not proposing new variants/props on any ofthe five — that's 0.2's job.**States already covered, unchanged:** Button already has default/hover(via CSS var)/disabled/loading; TextField has default/error/disabled(native); Banner has its three tones. Nothing newrequired here — 0.1 doesn't add new components.## Explicitly out of scope for 0.1Breakpoint values (real pixels) — not needed here since the kitchen-sink page has no responsivelayout switch (single scrolling column, reviewed at both widths but not laid out differently bywidth). Real breakpoint decision deferred to 0.2 (kitchen-sink at "mobile and laptop widths") and0.3 (sidebar vs. bottom-nav split) — for reference when that's planned, the reference build's ownTailwind usage (`wireframe/JBC Frontend Reference - Friend Build`) anchors exclusively on `lg:`(Tailwind default 1024px), a real data point to reuse rather than invent then.---## Verification / evidence plan (rule 2) — Claude Code gathers this, Technical Lead does independent re-verification after1. `apps/admin-v2/src/auth/applyAccentRamp.test.ts` — pure unit proof the ramp is genuinely   tenant-driven (two different hexes → two different 9-step maps). `pnpm --filter admin-v2 test`.2.
