Sub-slice 0.1 — Design tokens, theming, logo**Real work:**1. Replace `styles.css`'s hardcoded `--av2-accent*` values with real output from `colorRamp.ts`, fed by the signed-in tenant's real `themeColor` (JBC: `#166534`, per `docs/theming_path_b_kickoff.md`'s already-recorded value). Reuse the ramp utility as pure logic — no `ui-shared` component or `TenantProvider` dependency, matching the earlier confirmed decision to keep admin-v2's component layer local.2. Resolve tenant identity the way Slice 1 already established — from the admin JWT, via the existing `GET /tenants/:id` endpoint (added in Slice 1 step 4.3) — not `ui-shared`'s hostname-based `TenantProvider`.3. Author real values for spacing scale, radius scale, and shadow depth as CSS custom properties alongside the existing color tokens, informed by the reference build's actual rendered density (not invented from scratch, not lifted as literal CSS either).4. Logo: extend the existing `Tenant.logo` convention (`/logo-jbc.png`, root-relative static asset — same pattern `docs/theming_path_b_kickoff.md` already established for guest-pwa) to admin-v2's login screen and nav shell header.5. **Real edge case already known from guest-pwa's own theming work, worth checking here before it repeats**: the dynamic PWA manifest problem (`sizes: '512x512'` hardcoded against JBC's real 1600×1425 JPEG) was guest-pwa-specific because guest-pwa injects a manifest per-tenant at runtime. Admin-v2's manifest is static (`public/manifest.json`, Slice 1 step 4.5) and — today — single-tenant in practice, so this may not recur the same way. **Technical Lead should confirm rather than assume**: does admin-v2 need a real converted PNG icon now, or is this a non-issue given the static single-tenant manifest?**Open, real question for Technical Lead to raise at plan-mode time, not resolve unilaterally:** admin-v2's seed script (`tests/seed-admin-v2-data.mjs`) only provisions JBC today. Proving the ramp is genuinely tenant-driven — not hardcoded to JBC's green by coincidence — needs either a second synthetic tenant seeded for admin-v2, or an equivalent unit-level proof (feed `colorRamp.ts` a different hex, assert the CSS variables change). Recommend the unit-level proof as the primary evidence (cheaper, already how `colorRamp.ts` itself was verified) with a real-browser JBC pass as the visual confirmation — but this is worth stating explicitly in the plan doc rather than assumed.**Deliverable / sign-off unit:** a kitchen-sink token test page (dev-only route, excluded from the real nav) rendering: the full color palette in both light and dark, the typography scale, the spacing scale, border radii, shadow depths, and the real JBC logo. Reviewed by Bala on a real laptop browser and a real Android device, matching Slice 1's device rigor — not just automated contrast checks.---## 2. Sub-slice 0.2 — Generic reusable components**Depends on 0.1** — every component here is built against the token layer, zero new hardcoded colors.**Real gap against what a dense admin console needs**, beyond Slice 1's existing five (`Button`, `Card`, `TextField`, `Banner`/`InlineError`, `Spinner`/`LoadingState`) — informed by what the reference build's screens actually contain and what later module slices (Guest Management, Manage Members, Manage Court Groups, Subscription Ledger) will need:- **Modal/Dialog** — confirmations, forms-in-overlay (the reference build uses these extensively for admin actions).- **Table / dense data list** — admin's core surface (bookings, members, ledger rows); guest-pwa's `.card`-shaped components don't fit this need, which is exactly why the component layer stays local per the earlier decision.- **Select/Dropdown, Tabs** — filtering and section-switching, both visible throughout the reference build's admin screens.- **Badge/StatusPill** — booking/member/payment status, reusing the visual language of the existing `guest-member-pwa` `.status-pill` pattern conceptually (not the component itself) per rule 3.- **Avatar, EmptyState, Toast/inline notification, IconButton.**- **SidebarNavItem and BottomNavItem** — needed by 0.3, built here since they're generic, reusable primitives, not the nav shell's own logic.**Deliverable / sign-off unit:** the same kitchen-sink page from 0.1, extended with every component and every variant, verified at both mobile and laptop widths — real interaction states (hover, focus-visible using the existing `--av2-ring` token, disabled, loading) checked, not just static rendering. Real-device pass, same rigor as 0.1.---## 3. Sub-slice 0.3 — Navigation shell + landing page**Depends on 0.1 and 0.2.****Real work:**1.
