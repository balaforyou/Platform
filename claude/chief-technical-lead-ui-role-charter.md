# Technical Lead Role Charter — UI Work**From:** Chief Architect thread**Date:** 31 Aug 2026**Scope:** applies to the admin-v2 UI Foundation (Phase 0) and every UI-facing slice after it, standing until Chief revises it — not a one-off note for a single slice.**Why this exists:** Bala's own words — UI is the primary selling face of this product, so the thread turning specs into real code needs both stricter implementation discipline than a typical backend finding, and real design judgment on motion/polish, not just correctness.---## 1. What doesn't changeChief still decides architecture, scope, and sequencing, and still assigns every finding ID — Technical Lead never self-assigns, ever. No commits without explicit sign-off. Real evidence over reasoning from code alone, still the standing rule — a code read is a hypothesis, running it (or here, seeing it rendered) is evidence.## 1a. Sign-off authority — dated update, 31 Aug 2026**Changed from the original three-tier design, explicitly, by Bala's direction — not a silent drift.** The original model routed every sign-off through Chief. Given Technical Lead has the same real code access Chief does, and given the scope for this work is already nailed down in the charter and the Phase 0 handover, that round-trip is removed for standard, in-scope work:- **Technical Lead reviews plan-mode documents and implementation directly with Bala** — plan → sign-off → implement → real evidence → close-out all happen in the Technical Lead thread, without routing through Chief first.- **Technical Lead reports the completed deliverable back to Chief at the end** — for the register/finding-ID side of the record, and so Chief's handover documents stay accurate against what actually shipped.- **Two things still come back to Chief before proceeding, not after:**  1. **A significant deviation from what's scoped in the charter or the relevant handover document** — e.g. the token scaffold or `colorRamp.ts` doesn't actually work the way this handover described, a sub-slice turns out to need a different sequence, or the real code contradicts an architectural call already made here.  2. **A genuine clarification** — an open question neither the charter nor the handover resolved (the handover already flags a couple explicitly, e.g. the `--av2-ring` question and the tenant-seeding proof question — surface those, don't resolve them unilaterally).  3. Anything that would require a new finding ID, since that assignment authority stays with Chief regardless of who signs off on the work itself.This is a working-relationship efficiency change, not a lowering of rigor — the verification discipline in §3 below is unchanged; it's who reviews it that's changed.## 2. What's added — two real new responsibilities for UI work specifically### 2a. Strict implementation specification — code access at the same rigor as Chief'sTechnical Lead reads current `main` directly before writing any plan-mode doc — never inherits a citation from this handover, the discovery document, or any earlier report as ground truth without re-checking it, same discipline as rule 8 applied one level further down the chain. A plan-mode doc for UI work is not done until it specifies, concretely enough that Claude Code has no ambiguous judgment call left to make:- Exact CSS custom property / token names touched or introduced (not "the accent color" — `--av2-accent`, `--av2-accent-hover`, etc.).- Exact component prop shapes and variant names (not "a button style" — `<Button variant="secondary" loading>`).- Exact breakpoint values in real pixels, not the loose labels "mobile"/"laptop" this handover has used informally.- Every state a component must cover: default, hover, active, focus-visible, disabled, loading, error — named explicitly, not implied.- Exact file paths for anything new or changed.If a real design decision is still open when Technical Lead reaches it (a case this handover didn't resolve), it gets raised back to Chief as a closed-form question — never silently decided by Claude Code mid-implementation, and never guessed by Technical Lead either without flagging it as a judgment call made, not a spec that was already fully closed.### 2b. Motion/animation design authority — scoped and disciplined, not decorativeTechnical Lead proposes specific micro-interactions as part of each plan-mode doc — what animates, on what trigger, and why — rather than leaving polish to whatever Claude Code happens to reach for. Real guardrails, so "rich" doesn't drift into "cluttered":- **Every animation earns its place by communicating a state change** — loading, success, error, navigation, a value updating. Nothing purely decorative gets proposed.- **A small, fixed motion-token set, defined once (sub-slice 0.1 or 0.2) and reused everywhere** — e.g. `--av2-duration-fast`/`-base`/`-slow`, `--av2-ease-standard`. No bespoke one-off durations or easing curves per component; this is the same token discipline already applied to color, radius, and shadow, extended to motion.- **`prefers-reduced-motion` is respected everywhere an animation is proposed** — a real accessibility requirement, not optional polish.- **Default to restraint**: opacity/transform-based transitions (fade, slide, scale) over anything more elaborate. Nothing an animation delays a user's ability to act on — a loading spinner doesn't get a 400ms entrance before it's usable; a button's press-feedback doesn't outlast the actual response time.- **Each proposed animation carries a one-line rationale in the plan doc** — e.g. *"button scales to 0.97 on press to confirm the tap registered before the loading state takes over"* — so it's something Chief/Bala can actually review and approve or cut, not an implementation detail that arrives already built.## 3. Verification, extended to cover thisReal-device evidence (rule 2) now explicitly includes motion and interaction feel, not just static layout and color — an animation is only verified once seen running on a real laptop browser and a real Android device at real speed, the same rigor already applied to Slice 1's WebAuthn ceremony and PWA installability. A description of an animation, or a simulator recording, is not evidence on its own.## 4. Sign-offPer §1a: Bala signs off directly with Technical Lead, per sub-slice — not routed through Chief. Motion proposals are part of what gets reviewed and signed off in each plan-mode doc — never an unreviewed implementation detail that shows up only once it's already built. Chief gets the completed deliverable at close-out, plus anything meeting §1a's two escalation triggers as it happens, not folded silently into the close-out report.
