## Context

Immediately after F-088 Stage 2 (parts 2-5) shipped to production — both real JBC branches
cleared of disposable UAT data and flipped to `Asia/Kolkata`, `atLocalUtcDate` fixed to honor the
branch's real timezone — Bala began functional testing on the real production site: creating and
deleting a real `AvailabilityPattern` on one real branch/pool (`7d680518-fc68-4b4f-8639-1d8f1dc7f30b`
/ `54c44a14-ec5e-42b8-8c75-a463096f3495`) and observing the Guest Slot Inventory / guest booking
screens.

## Observation 1 — after creating a new pattern, today showed the wrong hours

Bala created a real `AvailabilityPattern` (`05:00-08:00 AM`, all 7 days) on the pool above. Future
dates correctly showed `05:00-08:00 AM` slots. **Today showed `6:00-9:00 PM` instead.**

**Root cause, confirmed by direct DB read, not assumed:** earlier the same session, this thread's
own F-088 live-verification pass queried `guest-inventory-grid` for *today's* date on this exact
pool, while the pool's *old* pattern (`06:00-22:00`, later deleted by Bala as part of "removing
guest slots") was still active. That query lazily generated a real day's worth of
`AvailabilityWindow` rows under the old pattern (`generatedFromPatternId = f9879534-...`) *before*
Bala's new pattern existed.

`ensureAvailabilityWindowsForDate` (`services/slot-engine/src/availabilityGeneration.ts`) is
**lazy and additive, never retroactive**: for any `(resourcePoolId, date)` pair that already has
generated windows, it skips creating anything new for a time slot that already exists at that
exact `(resourceId, startTime, endTime)` — it never deletes, reconciles, or re-tags a window
already sitting in the table when the pattern that would have produced it later changes. So:

- Today already had 17 windows spanning `00:30-16:30 UTC` (6:00 AM-10:00 PM IST, the *old*
  pattern's real range) from the earlier query. By the time Bala checked, morning hours had
  naturally elapsed, leaving only the evening tail (`6:00-9:00 PM`) still showing `guest-vacant`
  — that's exactly what was seen.
- The new pattern's own generation for today only produced *one* genuinely new row (the `5:00-6:00
  AM` slot, the only time in its range that didn't already coincide with an old-pattern window);
  the rest of its range (`6:00-8:00 AM`) silently landed on slots that already existed under the
  old pattern's tag and were skipped.
- Future dates (never queried while the old pattern was active) had no pre-existing windows, so
  they picked up the new pattern cleanly.

Confirmed zero real bookings on any of the 15 stale leftover windows before describing this as
safe to clear.

## Observation 2 — after deleting the pattern again, a wider version of the same thing

Bala deleted the new pattern. Checking across several dates:

- **Sep 19 (today):** evening slots still shown.
- **Sep 20-22:** morning slots (`5:00-8:00 AM`) still shown.
- **Sep 23 onward:** no slots.

**Same root cause, confirmed by direct DB read across the date range:**

| IST date | Windows | Tagged pattern | Why |
|---|---|---|---|
| Sep 19 | 1 | new pattern (`5-6 AM`) | generated while new pattern was active |
| Sep 19 | 16 | old, already-deleted pattern (`6 AM-10 PM`) | generated by this thread's own earlier verification query |
| Sep 20 | 3 | new pattern (`5-8 AM`) | generated while new pattern was active (queried during this thread's own verification pass) |
| Sep 21 | 3 | new pattern (`5-8 AM`) | same |
| Sep 22 | 3 | new pattern (`5-8 AM`) | same |
| Sep 23+ | 0 | — | never queried while any pattern existed, so nothing was ever lazily generated |

**Deleting an `AvailabilityPattern` has zero effect on windows it already generated** — those rows
are permanent once created, independent of the pattern row's own lifecycle (`generatedFromPatternId`
is a bare string, not a foreign key with cascade). This is arguably correct/deliberate behavior at
the mechanism level — you don't want a schedule edit to silently destroy windows that might carry
real bookings — but it means "delete the pattern" is not the same operation as "un-publish the
slots this pattern already created," and nothing in the product surfaces that distinction to an
admin. Confirmed zero bookings on all 26 (actually 27, one extra caught in the final count) leftover
windows before clearing.

**Also confirmed:** the admin-v2 Guest Slot Inventory grid (`guest-inventory-grid`) and the guest
booking screen (`GET /resource-pools/:id/availability`) read the exact same `AvailabilityWindow`
rows via `computeBranchGuestDay` — so they always agree with each other. This was the same side
effect showing up in both places, not two separate bugs.

## Cleared, real evidence

Both incidents cleared via a real reviewed script (not ad hoc SQL), `BEGIN`/`COMMIT`, before/after
counts:
- Incident 1: 15 leftover old-pattern windows for today, zero bookings confirmed before deleting.
- Incident 2 (superseding, ran after the pattern was deleted a second time): all 27 remaining
  windows on the pool deleted in one pass (covered Sep 19-22's full leftover set), zero bookings

**Cleared** (same disciplined way): 4 windows, zero bookings confirmed first, `BEGIN`/`COMMIT`,

## Observation 4 — "Live Guest Allocation" is not driven by the guest slot schedule at all

Raised while looking at the same Dashboard screenshots: what is "Live Guest Allocation" actually
showing, given the Slot Monitor above it says "no slots configured"?

**Confirmed by code read** (`services/slot-engine/src/index.ts`, the `guest-occupancy-dashboard`
route's `liveAllocation` computation): it always lists **every physical court (`Resource`) in the
pool**, one row per court, completely independent of whether any `AvailabilityWindow` or pattern
exists. For each court, it looks for a window covering *this exact instant* (`window.startTime <=
now && now < window.endTime`):
- No window covers now → status defaults to **`Open`**.
- A window covers now with a member block/booking → `Occupied (Member)`.
- A window covers now with a guest booking → `Reserved — <name>`.

**The card cannot distinguish "no guest slot exists right now" from "a real guest slot exists right
now and happens to be vacant."** Both render identically as `Open`. With zero guest slots
configured on either branch (this session's own testing state), every court still shows `Open` —
technically correct (nobody is occupying the court this second) but potentially misleading to an
admin reading it as "these courts are available for guests to book right now," which isn't
guaranteed to be true absent a real configured slot.

## Observation 5 — real court assignment silently falls back to a cosmetic label when capacity != real court count

Live-fire tested a fresh pattern end to end: created `06:00-09:00 AM` on pool `3025df55-...`
(`JBC – New Japan Badminton Court`), booked one slot via the real admin walk-in flow
(`2c66265f-...`, Sep 20) and one via Bala's real Google-authenticated self-service checkout
(`6dcfa4bb-...`, real Razorpay order `order_TdtXQ6yYwjSe7r`, `paid`, ₹600 — Sep 22). Both correct
and fully verified (capacity, pricing, payment capture, both dashboard/inventory views agreeing).

**Bala noticed the Inventory grid showed the Sep 22 booking as "Booked" on all three court
columns (A/B/C) simultaneously**, and separately that the booking confirmation names a specific
"Court 1" — the two seemed to contradict each other (one real slot booked, but three courts
marked occupied, and a numbered court with no visible tie to any of the three real ones).

**Root cause, confirmed by direct DB read + code read, not assumed:** both bookings recorded
`resourceId: null`, `courtSlotIndex: 1`. Traced to `assignPooledCourt`
(`services/slot-engine/src/index.ts:116-147`, F-205): **real per-court assignment only fires when
the pool's actual registered `Resource` count exactly equals its configured `capacity`.** This
pool has 3 real courts (Court A/B/C) but `capacity: 4` (set when the pattern was created) — since
`3 != 4`, the code's own documented fallback kicks in: `resourceId: null` plus F-186's original
purely cosmetic 1..capacity index. Two consequences, both now explained by one root cause:
- **"Court 1" on the guest's confirmation is not tied to any real court** — it's the cosmetic
  fallback index, not a real dynamic allocation, despite reading exactly like one.
- **The Inventory grid correctly renders a null-`resourceId` window against every court row**
  (there's no real court to pin it to) — so three columns showing "Booked" for one real booking is
  the grid behaving correctly *given* the fallback, not a rendering bug.

If the pool's `capacity` matched its real court count (3, not 4), F-205's real assignment would
have fired: a genuine `resourceId` would be recorded, "Court 1/2/3" would mean something real, and
the grid would highlight exactly one column instead of all three. **This is a genuine functional
gap, not just a display quirk** — an admin/staff member trying to match a guest's "Court 1"
confirmation to a physical court on site has nothing real to go on today, on this specific pool.

## Observation 6 — Inventory grid header should stay fixed while rows scroll

UI/UX observation, not a functional defect. On the Guest Slot Inventory screen (desktop), the
court column headers (`Court A`/`Court B`/`Court C`) scroll away with the rest of the grid once
the time rows exceed the viewport — Bala wants the header row pinned/sticky so it stays visible
while only the slot rows scroll vertically. No investigation needed; a straightforward `position:
sticky` treatment on the header row, same idea as the existing sticky time-column treatment on
mobile (F-256). Not designed or scoped here — just recorded so it isn't lost.

## Open question for consolidation — not decided here

Is "a pattern generates real windows that outlive the pattern itself, without any surfaced way to
tell an admin this happened" worth its own finding, or is it accepted behavior that just needs a
clearer mental model (and maybe a "regenerate/reconcile" action surfaced somewhere) rather than a
defect? Real candidate angles, none decided:
- A "preview before publish" step showing exactly what a new/edited pattern will change for
  already-generated dates, so an admin isn't surprised by stale leftovers.
- An explicit reconciliation action ("clear generated windows for this pool/date range") rather
  than requiring a direct DB script every time this comes up during testing.
- Leave as-is and document the mental model (patterns are append-only generators, not live
  schedules) prominently wherever patterns are edited.

Separately, is Observation 4 (Live Guest Allocation's `Open` conflating "no schedule" with "vacant
scheduled slot") worth its own finding, or a copy/label tweak (e.g. distinguishing "Open" from
"No slot configured")? Also not decided here.

Observation 5 reads like a real, standalone finding candidate rather than a UX question — the
capacity/real-court-count mismatch is a genuine pre-existing data-configuration issue (same class
as F-100's branch-timezone mismatch: a numeric setting silently disagreeing with reality), not
something this round's testing introduced. Whether the fix is "set this pool's capacity to 3" (an
operational correction, like F-100's timezone flip) or "make the mismatch impossible/surfaced at
config time" (a product gap) is Chief's call once consolidated.

Not proposing a design here — flagging for discussion once Bala's functional-testing pass is done
and everything found this round is consolidated together.
