# Findings Register — Running Log (reconciled 31 Jul 2026)

**Purpose:** One live place tracking every gap, bug, or open decision surfaced during review. Modeled on the BCC governance-trail discipline: nothing gets fixed silently and forgotten, nothing stays open without being visible.

**Process note, added after a real incident:** IDs F-018/F-019 were independently reused twice for unrelated findings, causing the more significant findings under those IDs to be silently lost from the register. Restored below under F-022/F-023. **Going forward: the reviewer alone assigns and tracks IDs — the coding agent reports findings back in plain description, never picks or writes an ID itself.**

**Process note, added 2 Aug 2026:** a heuristic UX/business-fit report's summary claimed "zero leaks anywhere" across all captured evidence, but one of its own cited JSON artifacts (`admin-01-resources.json`) directly contradicted this (`"allCaps": ["PER_PERSON"]`). The underlying issue was trivial (a legitimate pricing-enum value, not a real leak), but the blanket claim itself was inaccurate and wasn't caught before being used as supporting evidence. Lesson: summary claims in any report — not just code walkthroughs — need to be checked against their own cited evidence before being trusted, the same discipline already applied to technical walkthroughs under rule 8.

**Process note, added 6 Aug 2026:** F-043 (no admin UI existed for guest-slot scheduling at all) traces back to a real methodology gap flagged at the very start of this project — the BCC "Application Models" stage (wireframes/prototypes before code) was largely skipped, going from written business discovery straight to implementation kickoffs. A written requirement can read as "covered" while still being invisible in practice, because nobody had to visualize where it would actually live on a screen. F-043 was only found because the user personally tried to use the missing capability by hand, not because any review process caught it earlier. Lesson: for genuinely new capability (not a fix to something existing), a rough wireframe pass before the Technical Design kickoff is worth trying deliberately, specifically to surface "where does this actually appear on a screen" questions while they're still cheap to answer.
