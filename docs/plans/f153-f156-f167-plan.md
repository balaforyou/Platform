# F-153 & F-156 — slot-selection feedback on mobile, and the dashboard's unwired "Upcoming Slots" card

> **Status: APPROVED by Bala, 20 Aug 2026.** Committed before implementation so the reasoning
> behind the fix shape is git-durable rather than living only in chat.
> Two independent findings, two separate changes, two separate verifications. Both client-side only.

## Context

A founder walkthrough of the deployed JBC guest flow produced both findings. F-153: tapping a slot on a
phone appears to do nothing. F-156: a completed booking never shows up on the dashboard's upcoming view.

**One of the two register entries misdiagnoses its own cause, and the investigation had to correct it
before the fix shape could be known.** That correction is recorded below rather than absorbed silently.

---

## F-156 — the register's stated mechanism is wrong

F-156 reads: *"a cache or query-invalidation gap, not a data problem… Confirm where the upcoming list is
fetched and invalidate or refetch it after a successful confirmation."*

**There is no cache, no query, and no fetch.** Investigation established:

- `grep -rn "[Uu]pcoming"` across **both** frontend apps returns exactly one hit:
  `apps/guest-member-pwa/src/main.tsx:289`, the `<h3>Upcoming Slots</h3>` card on `MainDashboard`.
- That card's body is a hardcoded paragraph — *"No pre-scheduled matches today. Click "Book Court Now"
  to search for court times."* There is no `apiRequest`, no state, no effect behind it.
- `git log -S "No pre-scheduled matches today"` returns **one commit**: the baseline import. The card has
  never displayed a booking, for any user, at any point in the project's history.
- The guest PWA contains **zero** `useQuery`/`useMutation` calls. `QueryClientProvider` is mounted at
  `main.tsx:374` and the client configured at `:39`, but nothing consumes it. Every screen uses manual
  `useEffect` + `apiRequest`. So `invalidateQueries` would have had nothing to invalidate.
- `BranchDashboard.tsx` has no upcoming-bookings section at all — the kickoff's "confirm which component"
  step rules it out.
- `BookingHistory.tsx` (`/bookings/my`) **is not stale**: `fetchBookings()` runs in a `useEffect` keyed on
  `accessToken` (`:34-36`), the route unmounts on navigation, so it refetches on every arrival. It is the
  only surface that shows the booking — which is why the walkthrough found the booking there.

**The real mechanism: the card is an unwired placeholder.** The reported behaviour is not staleness that
navigation clears; it is a surface that has never been connected to data.

### The fix

Wire the card in `MainDashboard` (`apps/guest-member-pwa/src/main.tsx`) to real bookings, reusing the
fetch pattern **already present in that same component** — `loadMemberSession` (`:126-141`) is `apiRequest`
+ `useEffect` + loading/error state, and `BookingHistory.fetchBookings` (`:18-32`) hits the exact endpoint
needed. No new dependency, no query-library adoption.

1. Fetch `/slot-engine/bookings/my` with the existing `apiRequest` helper, keyed on `accessToken`,
   with its own loading and error state alongside the member-session state already there.
2. Filter to upcoming: `window.startTime > now`, status in `HELD | CONFIRMED | CHECKED_IN`.
   `CANCELLED` and `RELEASED_NO_SHOW` are excluded. **`HELD` is deliberately included** — holds carry a
   5-minute `heldUntil` TTL swept server-side (`slot-engine/src/index.ts:2944-2946`), so a `HELD` row on
   this card is a genuinely in-flight booking. Excluding it would blank the card for the seconds between
   payment and capture, reproducing the reported symptom on a fresh cause.
3. Sort ascending by `startTime`, render at most three (pool name, date, time, and a status label when not
   `CONFIRMED`), with a link to `/bookings/my` for the rest. Keep the existing empty-state copy for the
   genuinely-empty case.

**No invalidation call is needed, and none will be added.** `MainDashboard` is the `/` route element and
unmounts on navigation, so returning to the dashboard remounts it and refetches. The verification below
proves that rather than asserting it.

## F-153 — the feedback exists; it is unreachable

Mechanism confirmed in `apps/guest-member-pwa/src/components/CourtBooking.tsx`:

- The page is `grid grid-cols-1 lg:grid-cols-3` (`:197`). Below the `lg` breakpoint it collapses to a
  single column, so the right-hand rate summary renders **after the entire slot list**.
- The slot grid is `grid-cols-1 sm:grid-cols-2` (`:229`) — one card per row on a 375px phone. At ~100px
  per card, a 14-slot day puts the summary roughly 1400px below the viewport.
- Selection does fire real feedback: `:260-268` sets `--slot-selected-border` (brand colour) and
  `--slot-selected-surface` inline, immediately. That part works.
- What the user cannot see is the consequence: the placeholder at `:347-351` is replaced by the rate
  summary and the **"Hold & Proceed to Pay"** button (`:331`), entirely off screen, with nothing
  indicating the page changed.

There is no existing scroll-into-view pattern anywhere in this app to reuse (`grep` for
`scrollIntoView|scrollTo|useRef` across `apps/guest-member-pwa/src` returns nothing), so this introduces
the first one.

### The fix

1. Attach a `ref` to the rate-summary container (`:296`). Because that block **mounts** on selection, the
   ref is null inside the click handler — so the scroll runs in a `useEffect` keyed on
   `selectedSlot?.window?.id`, after the DOM has settled. That is what avoids the double-scroll the
   kickoff warns about: one scroll, after one render.
2. `el.scrollIntoView({ block: 'nearest' })`. `'nearest'` is chosen for its native semantics — it is a
   **no-op when the element is already fully visible**, which covers both regression cases with one rule
   and without hardcoding the `lg` breakpoint in JS: no jump on desktop (summary already in the right
   column), no jump when the tapped slot is above the fold. When the summary is below the viewport,
   `'nearest'` aligns its bottom edge to the viewport bottom, so the pay button lands on screen.
3. `behavior: 'smooth'`, downgraded to `'auto'` under `prefers-reduced-motion`.
4. **Echo the selected slot's time range inside the rate summary.** On a long list the tapped card
   necessarily leaves the viewport when the summary scrolls in — the two cannot co-exist on a 375px
   screen. This is additive copy inside the summary, giving the user confirmation of *what* they selected
   at the place they land. It does not touch F-146's slot styling.

**Not changed:** F-146's selection styling, the slot list layout, the `sm:grid-cols-2` breakpoint.

## Deliberately out of scope

- **F-152 stays untouched.** It remains blocked behind F-114; the player-count display is not modified.
- **`--slot-selected-surface` is `color-mix(… brand-primary 10%, #ffffff)`** — a 10% tint plus a 1px
  border. Legible, but weak on a phone in daylight. Strengthening it is explicitly out of scope per the
  kickoff; **recording it here as an observation, not fixing it**, for you to decide whether it deserves
  its own ID.
- **`PwaInstallPrompt` is `fixed bottom-6 … z-[100]`** (`:145`) and renders on every route via `Layout`.
  It would sit over any sticky bottom bar — which is why the sticky-action-bar alternative was rejected
  rather than the scroll approach. No change to that component.
- `BookingHistory.tsx`, which the investigation confirmed is a separate and already-correct surface.

### After-state, locally

Local `badminton_db` has **no future availability windows** (latest is `2026-08-19 21:00`, checked), so a
full slot day is seeded first — additively, with removable IDs, and read back before use.

| | F-153 expected after | F-156 expected after |
|---|---|---|
| Trigger | tap a mid-list slot at 375px | complete a booking, click "Go to Dashboard" |
| Result | summary + pay button scrolled into view | the booking is already listed on the card |
| Selection evidence | selected slot's time range shown in the summary | status label correct for `HELD` vs `CONFIRMED` |
| Regression | slot above the fold → no visible jump; desktop → no jump | previously-confirmed bookings still render, single fetch, no flicker |

The F-156 end-to-end runs **locally**, where `import.meta.env.DEV` is true and the "Simulate Payment"
control (`BookingPay.tsx:301`) exists — a real booking, really persisted, with no card entry. It is
completed **without navigating away and back**, since that is precisely what masks the finding.

Evidence is read from the live DOM and from database read-back, not asserted from the code.

**Honest limitation, stated up front:** this is Chrome device-width emulation at 375×812, not a physical
handset. If that is not good enough for sign-off, say so and I will hand you a build to check on a phone.
