# CLAUDE.md — deploy/gcp-vm/

Loaded automatically alongside root `CLAUDE.md` whenever a session touches files in this directory (the Caddyfile, docker-compose.yml, and .env that the traps below actually reference).

- **`sudo` strips shell-exported env vars.** Use `sudo -E` when a variable needs to survive into a privileged command (relevant for deploy-time SHA checks).
- **A stale `migrate` Docker image reports success while skipping real migrations.** Always confirm via the build-SHA verification (`packages/database/scripts/verify-build-sha.mjs`), not just "no pending migrations" output.
- **Caddy needs `SITE_ADDRESS` and the real `Caddyfile` — check the VM's actual running config, don't assume it matches the repo.** Config drift between the VM and repo has caused real, hard-to-diagnose deploy failures.
- **SSH-to-VM commands lose `||` and `$VAR` to the intermediate shells.** `||` is read as the shell OR, and `$VAR` expands in the wrong shell. For anything beyond a trivial one-liner, ship a file: `scp` a `.sql`/script file → `docker cp` it into the container → run it there.
- **`scp` from Windows carries CRLF, which breaks heredoc terminators on the VM.** Run `sed -i 's/\r$//' <file>` after copying, or the script exits producing zero output and no error.
- **Compose reports `Started` without applying a changed `.env`.** Use `up -d --force-recreate <service>`, then confirm with `docker inspect <container> --format '{{json .Config.Env}}'` rather than trusting `docker compose config`, which resolves values the container may never receive.
- **A `sed` mask that references the wrong URI scheme fails silently, not loudly.** `DATABASE_URL` uses `postgresql://`, not `postgres://` — a mask pattern built around the shorter, more intuitive-looking scheme name never matches, and `sed` just passes the unmatched line through completely unchanged, with no warning or error. This printed the real production password in plaintext (22 Aug 2026). Before trusting any masking pattern on a live credential, test it against a **known sample value first** and confirm the masked output actually differs from the input — a pattern that "looks right" is not evidence it matches.
- **`sudo` logs the full command line — including inline secrets — to `/var/log/auth.log`, independent of anything the command itself prints.** Passing a credential via `-e VAR=value` on a `sudo docker exec` (or any `sudo <cmd> --flag=secret`) is captured in cleartext by sudo's own audit logging the instant the command runs, regardless of whether the command's own stdout is masked, redirected, or discarded entirely. Rotating the `badminton` Postgres password (22 Aug 2026) leaked it into `auth.log` twice this way — once per rotation — found only while checking whether the *original* exposure had spread, not by design. **The robust fix**: never pass a secret as a command-line argument to anything invoked via `sudo`; feed it via a heredoc/stdin to a script or shell instead (`sudo <program> <<EOF ... EOF` or `sudo bash script.sh` reading the value from a file at runtime) — sudo does not log stdin content. `auth.log` itself can be surgically redacted after the fact (`sudo sed -i 's/<secret>/[REDACTED]/g' /var/log/auth.log`, run via a script file so the redaction command's own argv doesn't contain the secret either — **but see trap 9 below before doing this**) — but `journalctl`'s independent binary journal mirrors the same content and has **no safe per-entry redaction**; only vacuuming a whole time range removes it, which would also destroy unrelated legitimate audit data. Don't call an exposure "resolved" while that copy still exists — say so plainly instead.
- **Editing a live log file a running daemon has open requires a method that doesn't replace the inode — `sed -i`'s default write-new-then-rename does, silently.** The exact `sudo sed -i 's/<secret>/[REDACTED]/g' /var/log/auth.log` trap 8 recommends **broke `rsyslog`'s own logging** (22 Aug 2026): `sed -i` by default writes a new temp file and renames it over the original path, which orphans any file descriptor a running process already had open on the old inode. `rsyslogd` kept writing to that now-unlinked file — invisible at `/var/log/auth.log`, but still consuming disk and still growing — for the next 22 minutes, silently dropping every subsequent read of the "live" log to zero new entries with no error of any kind. Discovered only because a later cross-check found `auth.log`'s last entry stuck at a timestamp far behind the VM's actual clock; confirmed via `sudo ls -la /proc/<rsyslogd-pid>/fd/`, which showed the auth.log fd explicitly marked `(deleted)`. The orphaned content was still readable through `/proc/<pid>/fd/<n>` while the process stayed alive, which is what made recovery possible at all — that window doesn't last (it closes the moment the daemon restarts or reopens the fd itself). **The fix, in order of preference**: (1) edit via a method that preserves the inode instead of replacing it — `sponge` from moreutils (`grep -v ... file | sponge file`), or write to a temp file and `cat` it back over the original in place, never a plain rename-based `-i`, against any file a daemon might have open; or (2) if rename-based `-i` editing is unavoidable, **verify the daemon's fd afterward** (`ls -la /proc/<pid>/fd/ | grep <logfile>`, confirm no `(deleted)`) and send it `SIGHUP` (`sudo systemctl kill -s HUP rsyslog`) to force it to reopen the current path — don't assume a successful `sed -i` on a log file left the writer undisturbed.
